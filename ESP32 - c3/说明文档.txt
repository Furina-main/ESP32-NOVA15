ESP32 电子墨水屏徽章 - 项目架构与代码深度解析
一、 系统宏观架构
本项目在硬件资源极度受限（ESP32 仅有约 300KB 可用 RAM，且需运行 Web 服务器）的前提下，采用分层架构与异步事件驱动模型。

1. 硬件层 (Hardware Layer)
总线：屏幕（EPD）和外挂 Flash（ExtMem）共享 SPI 总线（SCK=4, MOSI=6, MISO=5）。

控制：通过不同的 CS（片选）引脚分离，屏幕 CS=10，外挂 CS=7。

2. 驱动层 (Driver Layer)
hardware.py：封装了屏幕底层的指令发送（_cmd、_data）和时序控制。针对 4 色墨水屏做了专门的 _REV 像素翻转处理。

extmem.py：自行实现了一套基于 SPI 通信的极简文件系统。不使用官方 LittleFS，是因为外挂 Flash 读写的 RAM 开销必须极低。

3. 服务层 (Server Layer)
microdot.py：微型异步 Web 框架，接收 HTTP 请求。

server.py：业务路由网关。负责处理上传、下载、列表获取、设备状态等 API。

webedit.py：在线代码编辑插件，提供文件读写 API 和防变砖的回滚逻辑。

4. 业务逻辑层 (Core Logic)
main.py：状态机中心。根据唤醒原因（冷启动/深睡唤醒/按键）决定进入服务器模式还是刷图模式。

boot.py：最先执行的脚本，执行代码回滚检测、关闭底层调试输出、初始化基础硬件。

5. 前端表现层 (Frontend)
基于 Alpine.js 和 HTMX，零依赖构建。使用 Canvas API 在浏览器端将裸数据（.bin）实时绘制成彩色图片。

二、 核心文件代码功能详解
1. boot.py —— 系统启动与防变砖机制
python
ROLLBACK_FILES = ('main.py', 'server.py', ...)
防变砖回滚机制：每次在 Web 编辑器里修改 Python 文件时，后端会生成一份 .bak 备份，并写入 boot_flag.txt 内容为 pending。

开机时 boot.py 检查标志位：

如果是 pending，则将其改为 testing。说明这是新代码的第一次启动。

如果是 testing，说明新代码启动失败或死机了（没来得及清除标志位），此时立刻将 .bak 覆盖回原文件，并强制重启。

关闭 IDF 调试：esp.osdebug(None) 防止原厂 C 库打印大量无用的日志，占用串口带宽。

3. hardware.py —— 核心屏幕驱动
python
def _gate_row(self, logical_y):
    # 屏幕像素点映射算法（A1 版本特殊排线）
    if logical_y < 300: return logical_y * 2
    else: return logical_y * 2 - 599
反色与翻转：4 色屏幕通过 2 bit 表示一个像素（00=黑, 01=白, 10=黄, 11=红）。由于硬件排线设计，数据在发送前，需要按字节进行 _REV 逆序处理，并且整行数据需要左右翻转（src_y = SCREEN_HEIGHT - 1 - y）。

_set_window()：Epaper 需要在局部刷新时指定 XY 坐标范围，代码中通过控制 0x83 指令来精确定位。

4. extmem.py —— 外挂 SPI Flash 文件系统
由于 ESP32 内存吃紧，无法挂载标准的 FATFS/LittleFS，作者手写了一套极简文件系统：

扇区结构：首部 0x000000 存放 EXS1 魔术字及文件目录表（包含文件名、偏移量、大小）。

分配策略：_alloc() 通过遍历文件表，寻找足够大的空闲地址块。

写入策略：Flash 必须先擦除（按 4KB 扇区）再写入（按 256B 页）。write_chunk() 内部实现了自动计算扇区、换页的逻辑。

5. server.py —— 极限内存 Web 服务
python
HEARTBEAT_TIMEOUT_S = 15
断连自动关机：前端每 5 秒发一次 /api/heartbeat。后端 _wifi_timeout_watcher 守护协程监控活跃时间，若超 15 秒无心跳（且不在上传文件状态），则调用 app.shutdown() 关闭 WiFi，让系统退出服务器模式，避免吃电。

分块上传：图片可能几 MB 大，upload_start 记录文件信息，upload_chunk 每次接收 8KB 数据直接写进外挂 Flash，upload_end 收尾更新目录。

图片下载防 OOM：

python
def stream_ext():
    for ch in ext.read_chunks(name, EXT_DL_CHUNK):
        if not ch: break
        yield ch
使用 Python 生成器（Generator），每次只读 2048 字节（EXT_DL_CHUNK = 2048），交给 microdot 发送。发送完立刻释放，绝不把整张图放进内存。

6. microdot.py —— 异步流式 HTTP 响应
_send_stream()：当 Response 的 body 是一个生成器时，框架会逐块通过 writer.write(pending) 发送数据。

发送后垃圾回收：每积累发完 1024 字节，强制 gc.collect()。这彻底解决了 ESP32 在并发下载时“瞬间爆内存（memory allocation failed）”导致返回空包（0 字节）的问题。

三、 前端核心技术解析 (Vue/JS 部分)
1. .bin 与 .jpg 的双轨制
.jpg（普通图片）：直接通过原生 new Image() 加载，用于网页背景、相册大图预览。

.bin（点阵数据）：通过 __decodeBitmap 获取 ArrayBuffer。使用 Canvas 逐像素读取 Palette（调色板）：

javascript
// 解析 2bpp 位图
var bp = x * bpp; 
var bi = rowBase + (bp >> 3); 
var code = (buf[bi] >> (8 - bpp - bo)) & mask;
将解析出来的 RGB 颜色写进 ImageData，再 putImageData 渲染到前端缩略图上。

2. 前端防崩溃：串行请求队列 _bmpQueue
javascript
async function _runBmpQueue() {
    // ...
    await new Promise(function (r) { setTimeout(r, 150); }); // 强制等待 150ms
}
当进入图库时，浏览器会瞬间请求几十张图片。如果并行请求，ESP32 直接瘫痪。因此前端实现了一个极其严格的队列：必须等上一张图完全接收并解析完，再歇 150ms，才允许发起下一张图的下载。这也是保证系统稳定的核心。

四、 关键技术难点与“神坑”记录
为什么页面有时候会报 NaN（位图大小错误）？

原因：早期版本 __getScreenCfg() 缓存了错误的配置层级（缓存了完整 config 而非 screen 节点），导致 width/height 为 undefined。

解决：在 main.js 中强制校验 sc.width 存在，若不存在提供写死的默认值作为兜底（768x552）。

为什么外挂图库有时会显示 0 字节？

原因：SPI 总线被硬件中断抢占（如刷屏），导致外挂文件系统 read() 返回空。

解决：在 server.py 中做了 if not ch: break 防御性编程，并在 microdot.py 中把发送块设为极小（1024字节），并高频 GC。

为什么播放列表里不能加 .jpg？

因为底层 hardware.py 的刷屏函数只认识 105,984 字节的纯点阵数据。误加 .jpg 会导致读取出错或者屏幕显示乱码。已在 list.html 前端过滤层、main.py 执行层做了双重拦截。
